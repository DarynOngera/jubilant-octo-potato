# Package lifecycle and contract

This page is the single map from an advisory to a reproduced, validated package.
It also records the invariants a package must satisfy and the exact work needed
to add a CVE or a target adapter.

If this page disagrees with the code, the code is authoritative. Update this
page in the same change that alters the contract.

> **Scope today.** The package format, lab lifecycle, probe protocol, validator,
> detector, and per-CVE report are generic in shape. The app image, `/echo`
> endpoint, `/admin/stats` payload, `/gc` endpoint, ingestion sources, and the
> global Bandit report are currently Bandit-specific. The adapter boundary is
> real for build/start/status/stop/provenance; it is not yet real for
> measurement, detection, or intelligence. See "Known boundary gaps" below.

## 1. Lifecycle

```text
data/advisories.json
        |
        |  vulnforge package scaffold <CVE>
        v
vulnerabilities/<CVE>/
  advisory.json
  package.json
  analysis/          root-cause.md, exploitability.json, attack-surface.md
  lab/lab.json       roles, versions, limits
  lab/compose.yaml   manual fallback; runtime Compose is generated
  poc/manifest.json  entrypoint, target roles, kwargs, metric, thresholds
  poc/exploit.py     run(ProbeTarget, **kwargs) -> ProbeResult
  detection/spec.json
        |
        |  vulnforge analyze <CVE> / triage / ingest
        v
vulnforge lab start <CVE>
        |
        |  adapter renders .vulnforge/labs/<CVE>/compose.yaml
        |  Docker starts vulnerable + patched services
        |  health/version check, then runtime.json + provenance.json
        v
vulnforge poc run <CVE>                 # one probe run, no evidence bundle
vulnforge validate <CVE> --runs 3       # A/B runs and evidence
        |
        |  evidence/runs/, evidence/telemetry/, evidence/logs/
        |  evidence/validation.json
        |  evidence/execution.json (artifact hashes)
        |  package.json status/verdict updated
        v
vulnforge detect <CVE>                  # offline rules over the captured evidence
        |
        |  detection/evidence.json
        v
vulnforge report <CVE>                  # report.md + report.json
vulnforge report --all                  # reports/technical-report.md
```

The supported order is:

```bash
vulnforge package validate <CVE>
vulnforge lab start <CVE>
vulnforge poc run <CVE>                 # optional single-run smoke test
vulnforge validate <CVE> --runs 3
vulnforge detect <CVE>
vulnforge report <CVE>
vulnforge lab stop <CVE>
```

`validate` needs a running lab. `detect` needs validation evidence. `report`
can be generated without detection, but the report will say detection has not
run; that is not a complete result.

## 2. What makes a package complete

There are three kinds of files:

- **hand-authored**: the contract input;
- **generated**: written by `lab`, `validate`, `detect`, `analyze`, or `report`;
- **documentation**: README files and prose.

```text
vulnerabilities/<CVE>/
├── advisory.json              hand-authored, schema-validated
├── package.json               hand-authored, schema-validated
├── README.md                  optional documentation
├── analysis/
│   ├── root-cause.md          hand-authored, required by the loader
│   ├── exploitability.json    hand-authored, schema-validated
│   ├── attack-surface.md      hand-authored, required by the loader
│   ├── root-cause.generated.md generated by `vulnforge analyze`
│   └── commits/               generated by `vulnforge analyze`
├── lab/
│   ├── lab.json               hand-authored, schema-validated
│   ├── compose.yaml           optional manual fallback; runtime Compose is generated
│   └── provenance.json        generated by `lab build`/`lab start`
├── poc/
│   ├── manifest.json          hand-authored, schema-validated
│   ├── exploit.py             hand-authored probe entrypoint
│   └── README.md              optional documentation
├── tests/                     required directory; no standard test template yet
├── detection/
│   ├── spec.json              hand-authored, schema-validated
│   ├── evidence.json          generated by `vulnforge detect`
│   └── README.md              optional documentation
├── evidence/
│   ├── execution.json         generated by `vulnforge validate`
│   ├── validation.json        generated by `vulnforge validate`
│   ├── runs/                  generated by `vulnforge validate`
│   ├── telemetry/             generated by `vulnforge validate`; each record
│   │                          includes a validation ID, target/image identity,
│   │                          UTC run times, and the captured telemetry
│   ├── logs/                  generated by `vulnforge validate`
│   └── README.md              excluded from the hash manifest
├── report.md                  generated by `vulnforge report`
└── report.json                generated by `vulnforge report`
```

### Current enforcement versus the complete contract

`vulnforge package validate` enforces the schemas plus the file checks in
`src/vulnforge/packages.py`. It does **not** require every generated artifact.
Use this table when deciding whether a package is complete for a verdict, not
just valid as a draft.

| Status | What must exist | Generated by |
|---|---|---|
| `draft` | `package.json`, `advisory.json`, `lab/lab.json`, `poc/manifest.json`, the probe entrypoint, `detection/spec.json`, `analysis/root-cause.md`, `analysis/exploitability.json`, `analysis/attack-surface.md`, `tests/` | hand-authored |
| `lab-ready` | above + `lab/provenance.json` + a started runtime under `.vulnforge/labs/<CVE>/` | `lab build` / `lab start` |
| `poc-implemented` | above + a working `poc/exploit.py` | hand-authored |
| `validated` / `inconclusive` | above + `evidence/validation.json`, `evidence/execution.json`, `evidence/runs/`, `evidence/telemetry/`, `evidence/logs/`, `detection/evidence.json`, `report.md`, `report.json` | `validate`, `detect`, `report` |

The loader enforces this table through `src/vulnforge/contract.py`; the package
schema and the file checks in `src/vulnforge/packages.py` use the same table.
For a `validated`/`inconclusive` package, `package validate` now requires the
validation bundle, detection evidence, and both report files.

`lab-ready` and `retired` are valid schema values, but no current command writes
them. Apart from `vulnforge validate` setting `validated`, `inconclusive`, or
`poc-implemented`, status transitions are manual.

## 3. Five invariants

A package is complete only when all five hold.

1. **Identity.** The directory name, `package.json.cve`, `advisory.json.cve`,
   `lab/lab.json.cve`, `poc/manifest.json.cve`, and `detection/spec.json.cve`
   all agree. The adapter name in `package.json.adapter` and
   `lab/lab.json.adapter` agrees too. `target` is accepted as a legacy alias.
2. **Exact pair.** `package.json.versions.vulnerable` is the last affected
   release; `package.json.versions.patched` equals `versions.first_fixed`; both
   match `lab/lab.json.versions` and the lab target roles. The probe's
   `targets` map points each role at the corresponding lab target name.
3. **Lab shape.** `lab/lab.json` contains exactly the roles the validator will
   run (`vulnerable` and `patched`). The adapter renders the Compose file; no
   hand-authored host or port is used by the probe. The probe reads the runtime
   written by `lab start`, not `config/research.yaml`.
4. **Probe + predicate.** `poc/manifest.json` names a loadable entrypoint,
   declares the metric and `kwargs`, and carries the single machine-readable
   predicate in `thresholds`: `mode`, `vulnerable_min`, `patched_max`,
   `min_samples`, `max_cv`, and `min_ratio` when relative. The free-text
   `package.json.validation.predicate` must quote those same numbers.
5. **Evidence + detection + report.** For a `validated` or `inconclusive`
   package, the evidence bundle, `detection/evidence.json`, `report.md`, and
   `report.json` are present and regenerated from the current runs.
   `package.json.validation.last_verdict` matches `evidence/validation.json`'s
   verdict, and the report does not claim a verdict the evidence does not
   support.

## 4. Adding a CVE package

Start with:

```bash
vulnforge package scaffold <CVE>
```

That creates a valid `draft` package with the advisory materialized from
`data/advisories.json`, the derived last-vulnerable/first-fixed pair, a
generated `lab/compose.yaml`, a probe template, a detection-spec template, and
the required analysis/test scaffolding. It also works with explicit versions:

```bash
vulnforge package scaffold <CVE> --vulnerable 1.11.0 --patched 1.11.1
```

After scaffolding, use `vulnerabilities/CVE-2026-111101/` as the closest
template for an HTTP/1 memory effect and `vulnerabilities/CVE-2026-116078/` for
HTTP/2.

### Files that must change

| File | What to change |
|---|---|
| `advisory.json` | Materialize the catalog record; include `schema_version`, `cve`, title, affected ranges, `fixed_in`, track, commits, references, provenance. |
| `package.json` | Set `target`, `versions.vulnerable`, `versions.patched`, `versions.first_fixed`, `versions.affected`, paths, and a validation predicate that matches `poc/manifest.json.thresholds`. |
| `lab/lab.json` | Set adapter name, app path, roles, versions, target names, and limits. |
| `lab/compose.yaml` | Optional manual fallback. If you keep one, update versions, ports, caps, and environment by hand; the supported path generates its own Compose file. |
| `poc/manifest.json` | Set `entrypoint`, role-to-lab-target names, `kwargs`, `metric`, `thresholds`, `runs`, `disruptive`. |
| `poc/exploit.py` | Implement `run(target: ProbeTarget, **kwargs) -> ProbeResult`; read the dynamic runtime; emit the declared metric and the observations detection consumes. |
| `detection/spec.json` | Select rule IDs, thresholds, and expected results for both roles. |
| `analysis/*` | Write `root-cause.md`, `exploitability.json`, `attack-surface.md`; run `vulnforge analyze` for commit diffs and the generated scaffold. |
| `tests/*` | At minimum keep the directory; package-local executable tests are not standardized yet. |
| `report.md` / `report.json` | Generate; do not hand-edit. |
| `lab/app/locks/mix-<version>.lock` | Add both versions when the target is Bandit. The current repository only contains locks for 1.13.1, 1.14.0, and 1.14.1. |

### Copy versus change

- **Copy and adapt:** `README.md`, `poc/README.md`, `detection/README.md`,
  `evidence/README.md`.
- **Change:** `advisory.json`, `package.json`, `lab/lab.json`,
  `lab/compose.yaml`, `poc/manifest.json`, `poc/exploit.py`,
  `detection/spec.json`, the three required analysis files.
- **Generate:** `lab/provenance.json`, `evidence/*`, `detection/evidence.json`,
  `report.md`, `report.json`.

### Worked example: CVE-2026-39803

The catalog says `>= 1.4.0 and < 1.11.1`, fixed in `1.11.1`. Use vulnerable
`1.11.0` and patched `1.11.1` (both are present in
`data/lab-checkpoints.json`). That means:

1. Add `lab/app/locks/mix-1.11.0.lock` and `mix-1.11.1.lock`; they do not exist
   today. `lab start` will fail provenance if the adapter's lockfile is missing.
2. Set the package/lab pair and both lab targets to those versions.
3. Reuse the `/echo` endpoint; `MAX_BODY_LENGTH` already exists in the lab app.
4. Choose a metric that distinguishes "cap enforced" from "cap ignored." The
   current four detection rules are memory/frame/duration/process rules; they
   do not directly measure a declared length cap. A new rule, or a different
   observable, may require a core change. Do not pretend an existing rule
   covers it.
5. Because this CVE affects versions before the current lab's 1.13.1, the
   manual `lab/compose.yaml` fallback and the static `lab/app` build need the
   older versions too. The generated package lab uses the adapter lockfile, so
   the lockfiles are the critical missing piece.
6. Run the normal sequence: `package validate`, `lab start`, `poc run`,
   `validate`, `detect`, `report`, `lab stop`.

### Probe observation contract

`vulnforge validate` only needs a metric named by `poc/manifest.json`. The
offline detector additionally expects the probe's `observations` to contain:

- `one_byte_result` — the attack connection's counters;
- `control_result` — the large-frame/large-chunk control counters;
- `benign_pool` — a list of baseline connections;
- `telemetry.attack` — a list of samples with `process_count` and
  `top_process_memory`.

If a new probe does not emit these keys, detection will be incomplete even if
validation succeeds. This contract is not currently declared in
`schemas/probe.schema.json`; it is defined by `src/vulnforge/detect/runner.py`.

## 5. Adding a target adapter

The real protocol is `src/vulnforge/targets/base.py`, not the older snippet in
`docs/vulnforge-architecture.md`. Implement:

```text
constructor(repo_root=..., app_dir=...)
name
base_image
app_dir
repo_root                 # required by provenance
image_tag(cve, role, version)
build_args(version, cve, role)
labels(cve, role, version, git_commit)
lockfile(version)         # Path | None
version_from_stats(stats) # str | None
service(target, service, limits) -> dict
health(target) -> (bool, detail)
stats(target) -> dict | None
measurement() -> MeasurementSpec
intelligence() -> IntelligenceSpec
container_ports() -> (app_port, admin_port | None)
```

`service()` must return a Compose mapping with at least:

- `container_name`
- `image` and `build.context`
- `ports` (loopback-bound)
- `mem_limit`, `cpus`, `pids_limit`
- `read_only`
- `cap_drop: ["ALL"]`
- `restart: "no"`
- `security_opt` and any target-specific environment.

`version_from_stats()` must extract the version that `lab start` checks against
`lab/lab.json`. `lockfile()` may return `None` for targets without a lockfile.

### Measurement

The adapter now supplies a `MeasurementSpec`:

```python
MeasurementSpec(
    stats_path="/stats",
    health_path="/healthz",
    gc_path="/gc",          # None means no forced-GC endpoint
    reader=read_beam_stats, # normalize the target's JSON payload
    use_app_listener=False, # True for single-listener targets
)
```

`ProbeTarget` uses those paths and the reader, so the core no longer parses
`erlang_memory` itself. `MemorySampler` and `capture_benign_pool` both go
through the spec. The toy adapter uses `read_toy_stats` and
`use_app_listener=True`; it is now a native, non-BEAM measurement proof.

### Intelligence

`intelligence()` returns an `IntelligenceSpec` with the OSV
ecosystem/package, GitHub repository, and advisory URL. `vulnforge ingest`
and `vulnforge analyze` read those coordinates instead of hardcoding one
target. A target with no OSV coordinates (the toy adapter) is refused with a
clear error.

### What still blocks a non-BEAM adapter

- `ServicePlan` still carries both `app_port` and `admin_port`, and the
  orchestrator allocates both. `use_app_listener=True` makes the probe use the
  app listener for stats, but a single-listener target still has a dead admin
  port in runtime/provenance until the plan model is generalized.
- Detection still expects the probe observation keys documented below, not a
  target-declared observation schema.
- Report formatting still hardcodes the two memory metric names.
- Ingestion and the global report remain Bandit-specific.

The toy adapter is a real second implementation of the lab lifecycle and now
the measurement contract, but it still has no package/probe/evidence run, so it
does not prove validation, detection, or reporting.

## 6. Vocabulary

| Term | Meaning in this repository |
|---|---|
| **Package** | The whole `vulnerabilities/<CVE>/` tree. |
| **Adapter** | The target implementation under `src/vulnforge/targets/<name>/`. This is `package.json.adapter`; `target` remains a legacy alias. |
| **Role** | `vulnerable` or `patched` — the A/B position in a package lab. |
| **Target** | A concrete lab instance: a role plus a name, version, and URLs. Also used in `targets/` for the adapter concept; read it from context. |
| **Probe** | The executable artifact implementing `run(ProbeTarget, **kwargs) -> ProbeResult`, plus its `poc/manifest.json`. |
| **PoC** | The package's research artifact (`poc/`) and its report. The probe is the implementation inside it. |
| **Exploit** | The current filename `poc/exploit.py`; legacy vocabulary for the probe entrypoint. |
| **Evidence bundle** | `evidence/execution.json`, `validation.json`, runs, telemetry, logs. |
| **Detection evidence** | `detection/evidence.json`, a separate artifact outside `evidence/`. |

## 7. Known boundary gaps

These are the places where the current code still falls short of the factory
model. Keep them visible until they are removed:

1. **Measurement is adapter-provided:** `MeasurementSpec` now supplies the
   stats/health/GC paths and the payload reader. Remaining gap: the two-port
   `ServicePlan` still allocates a separate admin listener for single-listener
   targets.
2. **Detection is probe-shape-specific:** `src/vulnforge/detect/runner.py`
   expects `one_byte_result`, `control_result`, `benign_pool`, and
   `telemetry.attack`.
3. **Report formatting is metric-name-specific:**
   `src/vulnforge/report/package_report.py` treats `attack_memory_delta` and
   `control_memory_delta` as MiB and everything else as a multiplier.
4. **Intelligence is adapter-driven; the global report is still Bandit-only:**
   `ingest` and `analyze` use the adapter's `IntelligenceSpec` (OSV
   ecosystem/package and GitHub repo). `reports/generate_report.py` still
   builds the Bandit catalog/report and is not yet target-generic.
5. **The package contract is split:** `docs/package-authoring.md`,
   `vulnerabilities/README.md`, `schemas/package.schema.json`, and
   `src/vulnforge/packages.py` do not require the same file set.
6. **The toy adapter proves lifecycle + measurement only:**
   `tests/test_adapter_contract.py` builds/starts/status/stops, and the toy
   reader is exercised in unit tests; it never validates or detects a toy
   package.
7. **`lab/compose.yaml` is optional:** the supported path generates its own
   Compose file from `lab.json` and the adapter. The checked-in file is only a
   manual fallback; new packages should not need to create it.
